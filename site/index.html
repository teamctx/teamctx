teamctx.
ambient team context · pre-release
The record, delivered exactly

See what changed before you touch the code.

Before you or your coding agent edit a file, teamctx checks the systems your team already uses and shows what moved around the work: a pull request touching the same file, CI that is failing or still running, an acceptance criterion that changed on the linked issue, a design doc that was replaced. You stay the one who decides.

Every result says what teamctx checked and what it could not confirm. There is no language model between the record and you, so the same inputs give the same result every time.

01
Why it exists

Wrong context through a trusted terminal is the expensive failure.

Coding agents made the work move faster than the team can track. So an agent edits a file an open pull request is already changing, builds on a spec that moved yesterday, or trusts a green build that is still running. Nothing crashed. Everything looked fine.

The context was wrong, and wrong context delivered through a terminal you trust is the expensive kind of failure. Two agents can be perfectly authenticated and still act on two different versions of reality. teamctx checks the record at the moment the work starts.

02
The four checks

Four checks before the first edit.

At the start of a task, on a new branch or a resumed session, teamctx reads metadata from the systems of record your team already uses and surfaces four things on its own.

02.1

Colliding pull requests and merge requests

If someone else has an open PR or MR changing a file you are about to edit, you see it first. Your own PR for the branch you are on is set aside with a note, so it never reads as an alarm.

02.2

Failing or unconfirmed CI on your branch

Failing checks are named. Checks that are still running are reported as unconfirmed, so a build in progress is never counted as green.

02.3

Acceptance criteria that moved

teamctx finds the linked issue from your branch name or commits, names how it derived it so you can judge, and tells you if the criteria changed since you started work.

02.4

Design docs you rely on that were replaced

A doc in your declared docs folder, or a Confluence page, that names a newer version surfaces before you build on the old one.

03
What appears

What you see before the first edit.

After a one-time teamctx onboard, this check runs by itself: it grounds the session before the first edit, keeps watch while you work, and speaks again when something actually changed. Agents get the same answer over MCP. Nobody types a command before an edit. The output is rendered straight from the record; the samples below are real output from the pipeline.

Where teamctx could not look, it says so plainly and tells you how to turn the check on. A gap is never folded into a clear.

05
Why you can trust it

Built so a clear result is worth trusting.

A tool you use to check your work has to be steadier than the work it checks. These four properties come from how teamctx is built.

No language model in the content path

teamctx normalizes, routes, and renders the record. It never rewrites what the record says, so what you read matches the source and cannot be talked into a false answer by anything in between.

Source-backed evidence

Every finding traces back to its source. Each one carries a handle that opens the original record, down to the pull request, issue, gate, or page, so anything teamctx surfaces can be checked against the system it came from.

Same inputs, same result

Given the same inputs, the verdict is identical every time. The result reproduces from a digest of what went in, which makes it something you can replay and audit.

Honest about coverage

Where teamctx could not look, it says so and how to fix it. A coverage gap is always reported on its own line, and it is never folded into a clear result.

teamctx reports what is currently true in the record. Whether that is the right thing to do is your call, and teamctx does not claim the record itself is correct. It delivers the record exactly.

06
Sources

Reads what you already have. Read-only.

teamctx reads metadata from the systems of record your team uses. It sees only what you can see. It does not read pull request bodies, comments, patches, or private messages, and it never writes to your source systems.

  • GitHub
  • GitLab
  • Jira
  • Confluence

Each source is added only after it proves the same honest coverage behavior. More sources follow the same bar.

07
Setup, once

Set it up once. Then it just appears.

teamctx is pre-release. Install from source and set it up once. That is the last command anyone runs: from then on, team context is ambient. It shows up on its own, before the work starts.

one-time setup
$ git clone https://github.com/teamctx/teamctx
$ cd teamctx
$ pip install -e .

# one-time setup: detects the repo, writes a shareable .teamctx/config.json,
# installs the Claude Code reflex hook, and reports your credential
$ teamctx onboard

# that's it. you never run another command: from now on, team context
# appears by itself: at the start of a session, and again the moment
# something relevant changes while you work.

It runs by itself, and keeps watching. The hook teamctx onboard installs is opt-in. It grounds the session before its first edit, then quietly re-checks at an interval and speaks again when the answer actually changed, re-stating any standing gap rather than forgetting it, so silence means checked and unchanged within the interval. It never blocks an edit. When the world moves mid-session, what appears is exactly the change:

teamctx, while you work
since you started: GitHub PR #7 appeared, touching src/auth/token.py

Any agent can also call the work_start tool over MCP through teamctx-mcp, so credentials stay on the server side.
