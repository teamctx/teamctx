Context checks for coding agents·open source·pre-release

See what changed before you touch the code.

Before you or your coding agent edit a file, teamctx checks the systems your team already uses and shows what moved around the work: a pull request touching the same file, CI that is failing or still running, acceptance criteria that changed on the linked issue, a design doc that was replaced. You read source-backed evidence and stay the one who decides.

What it checks Quickstart

Every result says what teamctx checked and what it could not confirm. There is no language model between the record and you, so the same inputs give the same result every time.

Why it exists

Coding agents made the work move faster than the team can track. So an agent edits a file an open pull request is already changing, builds on a spec that moved yesterday, or trusts a green build that is actually red.

The context was wrong, and wrong context delivered through a terminal you trust is the expensive kind of failure. Two agents can be perfectly authenticated and still act on contradictory pictures of the work. Nothing in the stack was checking whether what the agent believed was still true. teamctx checks it, at the moment the work begins.

What it checks

Four checks before the first edit.

At the start of a task, on a new branch or a resumed session, teamctx reads metadata from the systems of record your team already uses and surfaces four things on its own.

01

Colliding pull requests and merge requests

If someone else has an open PR or MR changing a file you are about to edit, you see it first. Your own PR for the branch you are on is set aside with a note, so it never looks like a collision with yourself.

02

Failing or unconfirmed CI on your branch

Failing checks are named. Checks that are still running are reported as unconfirmed, so a build in progress is never counted as green.

03

Acceptance criteria that moved

teamctx finds the linked issue from your branch name or commits, names how it derived it so you can judge, and tells you if the criteria changed since you started work.

04

Design docs you rely on that were replaced

A doc in your declared docs folder, or a Confluence page, that names a newer version surfaces before you build on the old one.

At work-start

What you see before the first edit.

After a one-time teamctx onboard, this check runs by itself: it grounds the session before the first edit, keeps watch while you work, and speaks again only when something actually changed. Agents get the same answer over MCP. Nobody types a command before an edit. The output is rendered straight from the record; the samples below are real output from the pipeline.

A clear result is itemized

When nothing is in the way, the output lists every check that ran. Each line is something teamctx actually looked at, so a clear result is something you can rely on.

teamctx, before the session's first edit to src/auth/token.py
Looks clear to start.
  Checked: no other open PRs touch your files; the linked issue's criteria are unchanged (issue #42 from your branch name); the docs you rely on are current; no failing checks found.

A finding comes with the next step

When something needs handling, you get the finding and the exact command to look at it, followed by the checks that came back clean.

teamctx, before the session's first edit to src/auth/token.py
Before you start, here is what to handle first:
  • Open PR #7 changed src/auth/token.py: look at it before you edit so you don't undo each other's work (gh pr view 7 --repo acme/widgets)
  Also checked: the linked issue's criteria are unchanged (issue #42 from your branch name); the docs you rely on are current; no failing checks found.

It says where it could not look

When teamctx cannot reach a source, it names the check it could not run, why, and how to turn it on. A gap in coverage is reported plainly and never hidden behind a clear result.

teamctx, before the session's first edit to src/auth/token.py
Heads up: I can't confirm the important things yet:
  • Open PRs and failing checks: teamctx couldn't reach GitHub. Either it has no access yet (set GITHUB_TOKEN, or GITHUB_TOKEN_FILE with a path to a token file) or it's a temporary connection issue. Until it's back you won't see colliding PRs or red CI on your files.
  Not checked: spec changes (no issue could be derived from your branch or commits; name one with --issue); docs (no docs root is configured; set work_start.docs_root to enable).

Your own PR is not a collision

The open PR for the branch you are standing on is set aside with an FYI instead of being flagged against you, so the tool does not cry wolf on your own work.

teamctx, before the session's first edit to src/auth/token.py
Looks clear to start.
  Checked: no other open PRs touch your files; the linked issue's criteria are unchanged (issue #42 from your branch name); the docs you rely on are current; no failing checks found.
  FYI: Your own open PR #12 for this branch touches these files; not flagged as a collision.
Across your sources

The same finding, wherever the work lives.

teamctx reads GitHub, GitLab, Jira, and Confluence today. A finding reads the same way whatever the source, in the words that source uses. This was validated live across GitHub, GitLab, Jira, and Confluence with a multi-actor test program and committed evidence.

one finding, four sources
GitHub
  • Open PR #7 changed src/auth/token.py: look at it before you edit so you don't undo each other's work (gh pr view 7 --repo acme/widgets)
GitLab
  • Open MR !7 changed src/auth/token.py: look at it before you edit so you don't undo each other's work
Jira
  • Jira PROJ-88 updated: description updated: re-check the criteria before you rely on them
Confluence
  • Auth service design was superseded by Auth service design v2: rely on the current one instead

GitLab speaks in merge requests, GitHub carries the gh command to open the PR, Jira and Confluence name the issue and the page. The check is the same underneath; only the words match the source.

Why you can trust it

Built so a clear result is worth trusting.

A tool you use to check your work has to be steadier than the work it checks. These four properties come from how teamctx is built.

No language model in the content path

teamctx normalizes, routes, and renders the record. It never rewrites what the record says, so what you read matches the source and cannot be talked into a false answer by a poisoned artifact.

Source-backed evidence

Every finding traces back to its source. Each one carries a handle that opens the original record, down to the pull request, issue, gate, or page, so anything teamctx surfaces can be checked against the system it came from.

Same inputs, same result

Given the same inputs, the verdict is identical every time. The result reproduces from a digest of what went in, which makes it something you can replay and audit.

Honest about coverage

Where teamctx could not look, it says so and how to fix it. A coverage gap is always reported on its own line, and it is never folded into a clear result.

teamctx reports what is currently true in the record. Whether that is the right thing to do is your call, and teamctx does not claim the record itself is correct. It delivers the record without distortion so you can judge on it.

Sources

Reads what you already have. Read-only.

teamctx reads metadata from the systems of record your team uses. It sees only what you can see. It does not read pull request bodies, comments, patches, or private messages, and it does not write to your systems.

Each source is added only after it proves the same honest coverage behavior. More sources follow the same bar.

Quickstart

Set it up once. Then it just appears.

teamctx is pre-release. Install from source and set it up once. That is the last command anyone runs: from then on, team context is ambient. It shows up on its own, before the work starts.

bash
$ git clone https://github.com/teamctx/teamctx
$ cd teamctx
$ pip install -e .

# one-time setup: detects the repo, writes a shareable .teamctx/config.json,
# installs the Claude Code reflex hook, and reports your credential
$ teamctx onboard

# that's it. you never run another command: from now on, team context
# appears by itself: at the start of a session, and again the moment
# something relevant changes while you work.

It runs by itself, and keeps watching. The hook teamctx onboard installs is opt-in. It grounds the session before its first edit, then quietly re-checks at an interval and speaks again only when the answer actually changed, so silence means checked and unchanged. It never blocks an edit. When the world moves mid-session, what appears is exactly the change:

teamctx, while you work
since you started: GitHub PR #7 appeared, touching src/auth/token.py

Any agent can also call the work_start tool over MCP through teamctx-mcp, so credentials stay on the server side.

For teams running more than one agent on a shared codebase, and the people who keep them from stepping on each other. The same engine serves a solo developer and a large team; the difference is configuration.
